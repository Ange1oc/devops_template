# Безопасность и надёжность

Инструмент меняет самое чувствительное на сервере: доступ по SSH, firewall, sudo. Его механизмы защиты делятся на четыре слоя: предохранители до изменений, подтверждение рискованных изменений с автоматическим откатом, транзакционный журнал с бэкапами и бережное отношение к чужой конфигурации.

## Предохранители

Предохранитель — проверка, которая останавливает модуль **до** любых изменений с кодом выхода 3. Он не зависит от `--yes` (этот флаг отвечает только на вопросы) и снимается лишь `--force`, когда администратор осознанно берёт на себя риск. Остановленный предохранителем модуль оставляет систему нетронутой: всё, что он успел записать, откатывается.

| Модуль | Предохранитель |
|---|---|
| preflight | ОС не Ubuntu или версия не 22.04/24.04/26.04; свободного места на `/` меньше `PREFLIGHT_MIN_DISK_GB` |
| ssh | `sshd_config` не включает `sshd_config.d/*.conf`; запрет паролей, когда ни у одного разрешённого пользователя нет `authorized_keys`; `PermitRootLogin no` без пользователя с ключом **и рабочим sudo**; `AllowUsers` исключает пользователя текущей сессии; новый порт уже занят; `SSH_CONFIRM=none` |
| firewall | `FW_SSH_FROM` не включает IP текущей сессии; `FW_CONFIRM=none` при удалённой сессии |
| docker | установлены конфликтующие пакеты при `DOCKER_REMOVE_CONFLICTS=no` |
| certbot | DNS доменов не указывает на этот сервер (`CERTBOT_DNS_CHECK`) |
| любой | `confirm_or_rollback` в режиме `none` без `--force` |

«Рабочий sudo» означает: пользователь в группе `sudo` и либо у него задан пароль, либо для него есть `NOPASSWD` в sudoers. Пользователь, созданный `adduser --disabled-password`, этому условию не удовлетворяет, и запрет root для него был бы потерей административного доступа.

В dry-run (`plan`) предохранители работают так же, как при настоящем применении; модули отмечают «планируемые факты» (пользователь будет создан, ключи будут добавлены, sudo будет настроен), поэтому план на чистом сервере показывает тот же результат, что и `apply`.

## Подтверждения опасных действий

Некоторые действия не блокируются, но требуют явного согласия (`confirm_danger`): в терминале нужно ввести слово `yes`, `--yes` принимает автоматически, без терминала и без `--yes` действие отклоняется (код 3). Все такие вопросы задаются до изменений модуля.

| Действие | Где |
|---|---|
| `NOPASSWD:ALL` для администратора | users |
| `PermitRootLogin yes` | ssh |
| включение UFW (с перечнем открываемых портов) | firewall |
| удаление `docker.io`/`containerd`/`runc` и других конфликтующих пакетов | docker |
| добавление пользователя в группу `docker` | docker |
| откат запуска по `RUN_ID` | rollback |

## Подтверждение доступа и таймер отката

После применения конфигурации sshd или включения UFW есть окно, в котором ошибка (закрытый провайдером порт, опечатка в `AllowUsers`, ключ не того пользователя) оставляет сервер недоступным. Механизм:

1. Модуль применяет изменение и вызывает `confirm_or_rollback`.
2. Взводится таймер отката **вне SSH-сессии**: transient-юнит `systemd-run --on-active=<TIMEOUT>s --unit ubuntu-bootstrap-rollback-<модуль>` (без systemd — отсоединённый `setsid`-процесс). Обрыв сессии таймер не останавливает.
3. Записывается `/var/lib/ubuntu-bootstrap/pending.env`: `RUN_ID`, `MODULE`, `DEADLINE`, `MECH` (systemd/setsid), `TIMER`, `DESC`.
4. Дальше зависит от режима (`SSH_CONFIRM`, `FW_CONFIRM`):
   - **auto, интерактивно**: обратный отсчёт с вопросом; `y` подтверждает, `n` или таймаут откатывает немедленно. Пока идёт отсчёт, можно открыть новую сессию и выполнить `confirm` — основной процесс это заметит.
   - **auto, без терминала** (`--yes`, cloud-init, CI): самопроверка на сервере — sshd отвечает баннером на новом порту через loopback, порт разрешён в UFW (для firewall — UFW активен и SSH-порты разрешены). Успех подтверждает, провал откатывает. Самопроверка не видит внешние фильтры (security groups провайдера).
   - **wait**: процесс завершается (код 0), таймер продолжает идти; `confirm` из новой сессии снимает его. Для Ansible/CI, которые переподключаются по новому порту.
   - **none**: без таймера; разрешён только с `--force`.
5. Подтверждение (`confirm`): таймер останавливается, `pending.env` удаляется, в состоянии модуля фиксируется `CONFIRMED_AT`, выполняется хук `mod_confirmed` (ssh закрывает старый порт в UFW).
6. Откат (таймер, `rollback --pending`, ответ «нет», неудачная самопроверка): записи журнала модуля воспроизводятся в обратном порядке — восстанавливаются файлы, выполняются команды отката (для ssh — повторное применение прежнего конфига с перезапуском сокета, удаление нового порта из UFW; для firewall — восстановление файлов правил и возврат UFW в прежнее состояние). Состояние модуля становится `rolled_back`, хэш конфигурации сбрасывается, событие уходит в journald.

Пока изменение ожидает подтверждения, новый `apply` завершается кодом 5: сначала `confirm` или `rollback --pending`.

### Перезагрузка в окне ожидания

`ubuntu-bootstrap-recover.service` (включается установщиком, `WantedBy=multi-user.target`, `ConditionPathExists=/var/lib/ubuntu-bootstrap/pending.env`) при загрузке выполняет `rollback --pending --boot`: неподтверждённые изменения откатываются, sshd перезапускается с прежним конфигом. У юнита намеренно нет `Before=ssh.socket`: откат сам перезапускает `ssh.socket`, и ordering-зависимость дала бы цикл задач systemd.

### Обрыв SSH во время применения

`SIGHUP` не прерывает работу: вывод перенаправляется в лог запуска, процесс продолжается в фоне. Дочерние команды (`apt-get`, `dpkg`) запускаются с игнорированием `SIGHUP`, поэтому пакетная операция никогда не обрывается на полпути. `SIGTERM`/`SIGINT` обрабатываются между шагами: текущая команда доводится до конца, запуск помечается `interrupted`, блокировка освобождается. `doctor` показывает такие запуски, `rollback RUN_ID` откатывает их вручную.

### Старый порт при смене SSH-порта

Новый порт открывается в UFW до перезапуска sshd. Старый порт остаётся открытым до подтверждения и закрывается только после него — удаляются исключительно правила с комментарием `SSH (ubuntu-bootstrap)`. Если старый порт был открыт чужим правилом, модуль предупреждает и не трогает его.

## Транзакции

Каждый запуск `apply`, `plan`, `wizard`, `config set|init` — транзакция:

- **блокировка** `flock` на `/var/lib/ubuntu-bootstrap/.lock`: второй экземпляр завершается кодом 5; блокировка не наследуется таймером отката и не залипает после `SIGKILL`;
- **каталог запуска** `/var/lib/ubuntu-bootstrap/runs/<RUN_ID>/` с `run.env` (статус, команда, версия, время, пользователь, dry-run) и `journal`;
- **журнал** — одна запись в строке, поля через `\x1f`: `M module` (начало модуля), `W path backup|-` (файл записан; `-` — файла не было), `D path backup` (файл удалён), `U argv...` (команда отката);
- **бэкапы** — `/var/backups/ubuntu-bootstrap/<RUN_ID>/<абсолютный путь>` с сохранением прав и владельца (`cp -a`), права каталогов 700;
- **атомарная запись**: содержимое пишется во временный файл в том же каталоге, права и владелец выставляются до появления файла по целевому пути, затем `mv`. Файл с тем же содержимым не перезаписывается (только права и владелец при расхождении), поэтому повторный запуск не трогает mtime и не перезапускает сервисы;
- **команда отката регистрируется до изменения**: при обратном проходе журнала сначала восстанавливается файл, затем выполняется команда (перечитать сервис, удалить правило, удалить пользователя). Командой отката может быть функция модуля — модуль загружается перед выполнением;
- **ошибка модуля** (ненулевой код `mod_apply`, провал `mod_verify`) откатывает записи этого модуля в обратном порядке, помечает его `failed` и останавливает запуск; `--keep-going` продолжает;
- **`rollback RUN_ID [--module M]`** воспроизводит журнал любого прошлого запуска; состояние затронутых модулей становится `rolled_back`;
- **dry-run** ничего не журналирует и не бэкапит: `file_write` печатает diff, `run` — команду.

Чего откат не делает: не удаляет установленные пакеты и не отменяет `apt-get upgrade`; сервисы, установленные модулем, при откате лишь останавливаются и выключаются (например docker), конфигурация возвращается к прежней.

## Что инструмент никогда не трогает

- Чужие файлы целиком: записываются только собственные файлы (`*ubuntu-bootstrap*`, `00-ubuntu-bootstrap.conf`) и блоки между маркерами `# BEGIN ubuntu-bootstrap <имя>` / `# END ...` внутри `/etc/fstab`, `/etc/hosts`, `/etc/ufw/after.rules`. Остальные строки этих файлов сохраняются байт в байт.
- Существующие правила UFW: добавляются только недостающие; чужие SSH-правила не удаляются даже при смене порта.
- `daemon.json` Docker: наши ключи добавляются, чужие (в том числе `data-root`, другой `log-driver`) сохраняются.
- `authorized_keys`: ключи дописываются, существующие строки остаются.
- Существующие пользователи не пересоздаются, пароли существующих пользователей не меняются (кроме установки отсутствующего пароля администратора по явному хэшу или с терминала).
- Конфиги пакетов при `apt upgrade`: `--force-confold`.
- Источник уже установленного nginx не меняется.
- Ничего не удаляется из `/var/lib/docker`.

## Доверие к внешним источникам

| Что | Как проверяется |
|---|---|
| Сам инструмент | только HTTPS/TLS 1.2+; релизы — `SHA256SUMS` и опционально GPG-подпись; `--sha256`; `bash -n` каждого файла; отказ от деревьев с симлинками; атомарная подмена |
| Ключ репозитория Docker | отпечаток `9DC858229FC7DD38854AE2D88D81803C0EBFCD88` сверяется до записи |
| Ключ репозитория nginx.org | отпечаток `573BFD6B3D8FBC641079A6ABABF5BD827BD9BF62` должен входить в список ключей файла |
| Ключи администратора с GitHub | `https://github.com/<логин>.keys` по TLS; каждый ключ валидируется по формату |
| Host keys GitHub для deploy-ключей | `https://api.github.com/meta` по TLS; для других хостов — `ssh-keyscan` с выводом отпечатков |
| wg-network | скачивается из того же репозитория и ref, что сам ubuntu-bootstrap, `bash -n` перед запуском |
| Загрузки вообще | `curl --proto '=https' --tlsv1.2 --max-time 120`, редиректы на http запрещены |

## Логи, аудит, секреты

- Полный лог запуска: `/var/log/ubuntu-bootstrap/<RUN_ID>.log` (600): команды и их вывод, записанные файлы с путями к бэкапам, ответы на вопросы, события отката.
- journald: `logger -t ubuntu-bootstrap` для старта, завершения, отказов, откатов, подтверждений — с именем пользователя, запустившего команду.
- Секреты: пароль администратора задаётся через `passwd` с терминала или crypt-хэшем, в лог не попадает; `ask_secret` не логируется; diff в dry-run маскирует `PASSWORD`, `TOKEN`, `SECRET`, `PrivateKey`. `--set ADMIN_PASSWORD_HASH=...` виден в `ps` на время команды — для секретов предпочтительнее файл конфигурации (600, root).
- Файлы состояния и конфигурации — 600/700, владелец root.
- `doctor` проверяет, что `/opt/ubuntu-bootstrap` принадлежит root и не доступен на запись остальным, так как таймер отката и recover-сервис выполняют код оттуда от root.

## Ограничения и остаточные риски

- Самопроверка `SSH_CONFIRM=auto` без терминала видит только сам сервер; фильтры провайдера она не проверит — для них `SSH_CONFIRM=wait` + `confirm` из новой сессии.
- Откат не удаляет пакеты и не отменяет обновления системы.
- `--force` снимает все предохранители сразу, а не выборочно.
- В контейнерах пропускаются swap, NTP-демон, snap; sysctl применяется «на лету» только для доступных ключей; UFW требует `NET_ADMIN`.
- Подпись релизов проверяется только при заданном `UBB_SIGNING_KEY_FPR`; без него доверие — TLS и `SHA256SUMS`.
- Таймер отката на системах без systemd — обычный фоновый процесс, перезагрузку он не переживает (recover-сервис тоже требует systemd).
- certbot автоматизирует только HTTP-01 (нужны публичный DNS и открытый порт 80); wildcard-сертификаты (DNS-01) не автоматизируются.
