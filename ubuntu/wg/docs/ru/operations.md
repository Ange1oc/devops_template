## Мониторинг

| Что | Как | Сигнал |
|---|---|---|
| Общее состояние | `wg-network doctor` | код 0 — норма, 1 — предупреждения, 2 — ошибки |
| Неприменённые изменения (расхождение состояния и конфига) | `wg-network plan` | код 10 |
| Peer | `wg-network peer list --json` | `state` каждого peer, `latest_handshake`, трафик |
| Узел | `wg-network status --json` | `up`, `state_valid`, `pending_confirmation`, `manual_edits`, `unapplied_changes` |
| Изменения | `journalctl -t wg-network` | кто и что поменял, с идентификатором снимка |

Минимальная проверка для агента мониторинга (Zabbix, Nagios, cron):

```bash
sudo wg-network doctor --quiet >/dev/null; echo $?          # 0 / 1 / 2
sudo wg-network peer list --json | jq -r '.[] | select(.state != "online" and .state != "disabled") | .name'
```

Peer без трафика не делают handshake. Простаивающий peer без keepalive показывается как `stale`, хотя с ним всё в порядке; peer, созданные wg-network, шлют keepalive каждые 25 с, поэтому для них `stale` означает «недоступен».

## Журнал аудита

Каждое изменение пишется в syslog/journald с тегом `wg-network`:

```
iface=wg0 user=alice peer-add name=worker1 address=10.50.0.2 key=... routes=none
iface=wg0 user=alice apply class=hot snapshot=20260131-101500-peer-add result=1
iface=wg0 user=root rollback mode=auto class=restart txid=...
```

`user` — пользователь sudo, если он известен. Приватные ключи и токены в журнал не попадают.

## Диагностика проблем

Начни с `sudo wg-network doctor`: он проверяет большинство причин из таблицы ниже и подсказывает, что выполнить.

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| Peer в состоянии `no-handshake` | неверный ключ; UDP-порт hub закрыт (UFW, облачный security group); неверный endpoint; peer не запущен | сравни `wg-network public-key` на peer с `peer show NAME` на hub; проверь порт снаружи; `doctor` на обеих сторонах |
| Peer был online, теперь `stale` | peer выключен или сменил сеть; у hub сменился IP | проверь peer; с DNS-endpoint таймер повторного резолва восстановит связь за ~2–3 минуты; иначе `peer set hub --endpoint` на peer |
| Peer не видят друг друга | hub не маршрутизирует или у peer только маршрут на hub | `set --forward on` на hub; `peer set hub --routes 10.50.0.0/24` на старых peer |
| У клиента exit node нет интернета | не включён NAT; выключен форвардинг на uplink; DNS на клиенте | `set --nat eth0`; `doctor` покажет состояние форвардинга и MASQUERADE; для сгенерированных клиентов задай `--dns` |
| TCP через туннель зависает, ping работает | MTU / PMTUD | MSS clamping для маршрутизируемого трафика включён; попробуй `set --mtu 1380` (PPPoE: 1412) |
| «изменён вручную», код 3 | кто-то правил `/etc/wireguard/<iface>.conf` | `plan --diff` покажет правку; перенеси её в команды wg-network или перезапиши с `--force` (ручная версия сохранится) |
| Код 5, «занят» | работает другой wg-network или изменение ждёт подтверждения | подожди или выполни `confirm` / `rollback` |
| Код 3, «заблокирована предохранителем» | изменение оборвало бы SSH-сессию | прочитай предупреждение; подключись иначе или используй `--force`, если уверен (таймер всё равно защищает) |
| Изменение откатилось само | никто не подтвердил за `CONFIRM_TIMEOUT` | состояние вернулось к прежнему снимку; в `history` есть снимок `rejected`, повторить: `rollback <id>` |
| «состояние ... повреждено» | файл состояния правили или он обрезан | в сообщении список проблем; исправь файл или выполни `rollback` к снимку |
| `doctor`: «peer в ядре отличаются от конфига» | кто-то выполнил `wg set` напрямую | `wg-network apply` вернёт ядро к конфигу (горячо) |
| `doctor`: нет drop-in `wg-network.conf` | программа запущена из каталога, доступного на запись не-root, или после установки ещё не было `apply` | установи через `install.sh`; drop-in добавится при следующем применении |
| `doctor`: время не синхронизировано | выключен NTP | включи NTP: если часы прыгнут назад, peer будут отвергать handshake, пока время не догонит |

Полезные низкоуровневые команды:

```bash
sudo wg show                                  # ядро: peer, endpoint, handshake, трафик
sudo wg-network show                          # действующий конфиг, секреты скрыты
sudo wg-network show --candidate              # что запишет следующий apply
journalctl -u wg-quick@wg0 -n 50              # ошибки запуска и остановки интерфейса
ip route show table all | grep wg0            # маршруты, поставленные wg-quick
sudo iptables -S | grep wg-network            # правила firewall, добавленные wg-network
```

## Восстановление

**Изменение отрезало мне доступ.** Ничего не делай: через `CONFIRM_TIMEOUT` секунд (по умолчанию 120) прежний конфиг вернётся сам, даже если твоей сессии уже нет. Если сервер перезагрузится раньше, прежний конфиг поднимется при загрузке.

**Нужно отменить последнее изменение.** `sudo wg-network rollback`. Для более раннего состояния: `sudo wg-network history`, затем `sudo wg-network rollback <id>`.

**wg-network убили посреди изменения.** Следующий запуск любой изменяющей команды найдёт незавершённую транзакцию и восстановит состояние из её снимка. `doctor` покажет её ещё до этого.

**Повреждён каталог состояния.** Каждая команда отказывается генерировать из него конфиг и перечисляет проблемы. Исправь указанные файлы или верни снимок: `sudo wg-network rollback <id>`. Снимки — обычные tar-файлы в `/etc/wireguard/wg-network/<iface>/snapshots/`.

**Сервер потерян.** Восстанови архив на новом сервере (`wg-network restore`), см. [Замена упавшего hub](scenarios.md#замена-упавшего-hub). Без архива создай новый hub и заново пригласи всех peer.

**Хочу перестать управлять интерфейсом через wg-network, но сохранить туннель.** Удали программу (`install.sh --uninstall`): сгенерированный конфиг самодостаточен, `wg-quick@<iface>` продолжит работать. Состояние останется в `/etc/wireguard/wg-network` на случай переустановки.

**Хочу полностью убрать интерфейс.** `sudo wg-network -i wg0 destroy`. Архив состояния и конфига сохранится в `/var/backups/wg-network/`.

## Обновление и удаление

| Действие | Команда |
|---|---|
| Обновить до последней версии установленного ref | `sudo wg-network self-update` |
| Обновить до конкретной версии | `sudo wg-network self-update --ref <тег-или-commit>` |
| Вернуть предыдущую версию | `sudo /opt/wg-network/install.sh --rollback` |
| Удалить программу | `sudo /opt/wg-network/install.sh --uninstall` |
| Установить из локальной копии | `sudo ./ubuntu/wg/install.sh --local` |

Обновление заменяет только программу в `/opt/wg-network`. Интерфейсы не перезапускаются, ключи и конфиги не трогаются. Если новая версия генерирует другую шапку конфига, следующее изменение перезапишет файл без перезапуска (способ `rewrite`). Состояние прежних версий переносится автоматически.

Удаление убирает программу, таймер, drop-in и автодополнение. Туннели продолжают работать, состояние остаётся в `/etc/wireguard/wg-network`, файлы `/etc/wireguard/*.conf` не удаляются. Без программы нет отката при загрузке для неподтверждённых изменений, поэтому перед удалением подтверди или откати их.

## Производительность

Что wg-network делает сам:

- **Только модуль ядра.** `doctor` предупреждает, если запущен `wireguard-go`: реализация в userspace в разы медленнее.
- **Быстрое восстановление после перезапуска hub.** Peer без заданного endpoint неизвестны hub, пока сами что-нибудь не пришлют, а потерю сессии они замечают только через `KEEPALIVE_TIMEOUT + REKEY_TIMEOUT` (~15 с). wg-network возвращает последние известные адреса и сам начинает handshake. Замер на тестовом стенде: трафик возобновился примерно через 5 мс вместо 16,4 с.
- **Стабильный порт при горячих изменениях.** `wg syncconf` с конфигом без `ListenPort` (любой узел-peer) выбирает новый случайный порт, как и `systemctl reload wg-quick@`. После этого hub до следующего keepalive (до 25 с) слал бы трафик на старый порт. wg-network сохраняет текущий порт.
- **MSS clamping** для маршрутизируемого трафика и NAT: без него TCP зависает там, где сломан PMTUD.
- **Форвардинг на конкретных интерфейсах** (`net.ipv4.conf.<iface>.forwarding`) вместо глобального `ip_forward`: по документации ядра (`ip-sysctl`) смена `ip_forward` сбрасывает остальные параметры IPv4.
- **MTU.** По умолчанию `wg-quick` берёт MTU маршрута минус 80 (1420 при 1500). `--mtu` нужен для PPPoE (1412) и туннелей поверх туннелей. `doctor` предупреждает о MTU больше 1420.
- **Keepalive только там, где нужен.** 25 с со стороны peer, которые могут быть за NAT; со стороны hub — нет.
- **conntrack.** На exit node `doctor` следит за заполнением `nf_conntrack`.

Чего wg-network сознательно **не** делает: глобальный тюнинг системы (`net.core.rmem_max`, BBR, `netdev_budget`, RPS, привязка к CPU). Эти параметры влияют на все сервисы хоста. Для модуля ядра WireGuard буферы UDP-сокета не на пути данных: пакеты обрабатываются в softirq до очереди сокета. Если тюнишь — меряй до и после (`iperf3` через туннель).

Масштаб: тесты гоняют hub с 250 peer. На тестовой машине применение всех 250 заняло около 7 с, добавление ещё одного peer — около 9 с, `status --json` — около 10 с. Передача данных идёт в ядре и от числа peer не замедляется; команды управления написаны на bash и растут линейно, поэтому при многих сотнях peer каждая команда займёт десятки секунд.

## Безопасность

- Держи программу там, куда может писать только root (`/opt/wg-network` от установщика). Команды, которые root выполнит позже (таймер отката, проверка при загрузке), запускают её. Копия в домашнем каталоге вызывает предупреждение, и drop-in загрузки не ставится.
- В каталоге состояния лежит приватный ключ; права каталога 700, ключа 600. Архивы (`backup`) и клиентские конфиги содержат секреты: храни их зашифрованными.
- Токены приглашений содержат preshared key peer. Передавай их через stdin, скрытый запрос или файл с правами 600, а не в чатах.
- Наружу открыт только UDP-порт hub. WireGuard не отвечает на неаутентифицированные пакеты, поэтому сканеры порт не видят.
- Peer по умолчанию изолированы. Маршрутизация между peer (`--forward`) и NAT — явные решения администратора.

## Ограничения

- **Таймер отката не проверяет связь.** Он откатывает изменение, если его никто не подтвердил. Автоматическое подтверждение с `--yes` доказывает, что интерфейс, адреса, порт и peer в ядре в порядке, но не то, что твой сервис доступен. Если это важно, используй `--wait-confirm` и `confirm` из нового подключения.
- **Предохранитель видит только SSH.** Сессии находятся через `ss` и `sshd -T`; другие сервисы, облачные firewall и security group ему не видны.
- **IPv6-форвардинг не включается автоматически** (он отключает приём router advertisement). `doctor` предупреждает, решение за тобой.
- **Firewall.** Порт открывается только в UFW (при firewalld печатается команда). Правила маршрутизации и NAT ставятся через `iptables`/`ip6tables` (бэкенд nftables у iptables работает, чистый nftables без iptables — нет). Хуки работают в режиме fail-open: ошибка правила iptables не роняет туннель; `doctor` покажет пропавшие правила.
- **Перезапуск прерывает все туннели интерфейса** на время перезапуска плюс один handshake. Peer за NAT, чей endpoint hub не знает, переподключаются в пределах своего keepalive.
- **Один hub на сеть**: нет отказоустойчивости и full mesh. Смена ключа hub требует `peer set hub --key` на каждом peer.
- **Откат при загрузке требует установленной программы** (её запускает drop-in). После удаления действует последний записанный конфиг.
- **Сообщения командной строки — на русском.** JSON, состояния и коды выхода от языка не зависят.
- **Не проверено:**
  - на виртуальных машинах (на тестовом хосте нет KVM) и на железе: systemd проверен в контейнерах с systemd в роли PID 1;
  - на Debian, RHEL и Alpine;
  - внезапное отключение питания: `kill -9` и перезагрузки проверены, сброс кэша страниц на диск — нет;
  - успешные `self-update` и `deploy --install` с загрузкой из GitHub: в тестах нет интернета, проверены только пути отказа.
